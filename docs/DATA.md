# Private data and execution order

All paths below are relative to the working root (repository root by default).
Data is intentionally excluded from Git. Output schemas retain Chinese column names
to remain compatible with the original research pipeline.

## Inputs

| Input | Location / essential columns |
| --- | --- |
| Broker statements | `data/raw/<year>/`: supported broker XLSX or GBK/GB18030 TXT layouts |
| Completed trades | `output/completed_trades.csv`, generated by FIFO matching |
| Hedge candidates | `output/arbitrage_candidates.csv`, generated by candidate identification |
| P/P candidates | `output/P跨期套利/P跨期套利全部组合.csv`, exported by filtering |
| Individual-contract market data | `data/market/yp_lseg_full_contract_history.csv`: `product,contract,ric,date,open,high,low,settle,last,volume,open_interest` |
| Continuation market data | `data/market/yp_lseg_continuous_history.csv`: `品种,RIC,日期,SETTLE,TRDPRC_1`; preserve original vendor fields |

The `open,high,low` columns must exist even when their values are unavailable.
The inherited market filenames keep the `yp_` prefix for schema compatibility;
the palm-oil loaders filter P. The files are NOT bundled. Contract examples are
`P2701`, `P2705`. Use unambiguous ISO dates and consistent numeric price units.
Prices generally prefer settlement and fall back to last price. Inspect the loaders
for their exact handling before supplying a new vendor schema.

P/P candidate filtering expects at least:
`A品种,B品种,A合约,B合约,A方向,B方向,重叠天数,组合开始,组合结束,识别得分`.
Later event analysis needs the full candidate export, including leg identifiers,
fees/profit, matched quantities and entry/exit information—not only those filter columns.
The original candidate producer is the schema reference. PostgreSQL option:
database `quant`, schema `strategy`, table `arbitrage_candidates`.

## Broker statement layouts

Use one account per working root for statistics and candidate analysis. FIFO matching
groups positions by account, but later account summaries do not provide separate
multi-account equity curves. Complete monthly statements, including reported month-end
equity, are needed by `analyze_trading_style.py`.

The supported Excel input is `.xlsx`, not legacy `.xls`. Keep the broker's original
layout, labels and date strings; renaming columns alone may not adapt another layout.

| Sheet / section | Required contents |
| --- | --- |
| `客户交易结算月报` | `交易月份` as `YYYY-MM`, `客户期货期权内部资金账户` |
| Monthly summary on that sheet | `上月结存`, `当月存取合计`, `当月盈亏`, `当月手续费`, `当月结存`, `客户权益`, `浮动盈亏` |
| `成交明细` | `交易日期`, `合约`, `成交序号`, `成交时间`, `买/卖`, `成交价`, `手数`, `开/平`, `手续费`, `平仓盈亏` |
| Optional execution columns | `实际成交日期`, `成交额`, `投机（一般）/套保/套利` |
| Cash-flow sections on the monthly sheet | `期货期权账户出入金明细` and `其它资金明细`, in the original export layout |
| `持仓明细`, for an earlier position snapshot | `合约`, `成交序号`, `买持仓`, `买入价`, `卖持仓`, `卖出价`, `实际成交日期` |

The monthly-summary lookup uses Excel rows 9–20; cash-flow columns and section
boundaries also depend on the original layout. Execution dates use `YYYY-MM-DD`,
times use `HH:MM:SS`, and directions use `买`/`卖`. Missing `成交额` means the parser
cannot derive a contract multiplier, which limits price-based PnL validation.

TXT exports use the supported whitespace-separated Chinese broker layout. A filename
such as `000001-202401账单.txt` identifies a synthetic example account and month.
Execution rows start with `YYYYMMDD HH:MM:SS`, followed by exchange, contract,
trade ID, buy/sell, hedge type, price, quantity, turnover, open/close, fee, PnL,
premium and settlement transfer. Required summary labels are `期初结存`, `期间入金`,
`期间出金`, `期间出入金合计`, `平仓盈亏`, `期间手续费`, `期末结存`, `资金权益`,
and `浮动持仓盈亏`. Decoding tries GB18030, UTF-8 with BOM and UTF-8.

Use lowercase `.xlsx`/`.txt` extensions for portability. The parser searches recursively
and excludes paths containing `anonymized`. More than one discovered statement for the
same account/month stops the run before writing output, including a TXT/XLSX pair.
Supply one complete statement per account/month; split statements need explicit
consolidation rather than arbitrarily discarding a file. This conflict check takes
place during discovery, before the requested year filter.
With no year arguments it selects 2026 only; set the years explicitly.
A missing/non-directory source or zero successfully processed statements stops with
a nonzero exit status and leaves existing outputs unchanged. A valid zero-trade
statement can still produce account data. Some row/file failures may still be recorded
while other statements succeed; the zero-processed guard is not a full quality gate.
Review `parsing_errors.csv`: a completed process does not mean every source row parsed.
Other broker layouts need parser adaptation before the statistics can be trusted.

## Full local sequence

From the repository root, after supplying your own data:

```powershell
python scripts/parse_statements.py --start-year 2019 --end-year 2026
python scripts/match_trades.py
python scripts/identify_arbitrage.py
python scripts/filter_p_calendar_spreads_pg.py
python scripts/analyze_p_calendar_entry_exit.py
python scripts/backtest_p_calendar_v1.py
python scripts/backtest_p_calendar_v2.py
python scripts/analyze_p_main_liquid_far.py
python scripts/build_p_daily_research_panel.py
```

Set years to your actual dataset. Inspect parsing errors before downstream research.
Missing positions at the dataset boundary may require `match_trades.py --prior-statement`
and the relevant source folder; see `--help`. The parsers are broker-layout-specific,
not a universal TXT/XLSX conversion utility.

When starting from an existing database, use
`python scripts/filter_p_calendar_spreads_pg.py --from-db` then the market-analysis stages.
The backtests/report stages depend on earlier output files, including baseline results.
They can refresh files under output; keep experimental runs in separate working roots.

Optional trade-style statistics:
`python scripts/analyze_trading_style.py`.
Then run `python scripts/build_style_report.py` to create the Excel report.
After `identify_arbitrage.py`, run `python scripts/build_arbitrage_report.py` for the
candidate report. Both default to `output/reports/` and accept `--data-dir`, `--output`
and optional `--preview-dir`. See [REPORTS.md](REPORTS.md) for all required inputs.

## PostgreSQL identifier preservation

`import_to_pgsql.py` reads account/trade/candidate/leg identifiers as text before
pandas can infer numeric types. Leading zeros and long numeric identifiers are
preserved. Literal identifiers such as `NA` and `NULL` remain text; an empty
identifier becomes a null value. Quantity, price and other numeric columns retain
the existing inference behaviour.

Identifier fields include the pipeline's English `*_id` columns, Chinese
account/contract/product fields, and names ending in `ID`, `编号`, `序号`,
`账号` or `账户`. Add any new identifier naming convention explicitly when
extending input schemas.

New database tables use SQL TEXT for these fields, including all-empty identifier
columns. When appending, both existing tables are checked before any writes:
identifier columns must be TEXT/VARCHAR-compatible, not numeric. An incompatible
column stops the import; the script does not migrate schemas or repair existing
rows. Review such a schema separately, retaining backups and using original CSVs
to restore any zeros already lost. Changing a numeric column to text alone cannot
recover them.

The `--write` opt-in, fail-on-existing default, and transaction covering both
imports remain unchanged. Appending is still not deduplicated.

## Local path configuration

Example: point only the market-data folder elsewhere without changing code:

```powershell
$env:FUTURES_MARKET_DIR = "E:\\private-futures-data\\market"
python scripts/analyze_p_calendar_entry_exit.py
```

Alternatively set `FUTURES_WORK_ROOT` to a folder holding `output/` and `data/`.
Explicit CLI path options, where supplied, override defaults. Environment changes are
read on process start. These are placeholder paths.
